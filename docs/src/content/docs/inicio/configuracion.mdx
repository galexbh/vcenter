## Perfiles de entorno

Cada entorno se define en `config/environments.json`. Este archivo contiene nombres de servidores internos y **no se versiona**; se parte de la plantilla incluida. `task setup` lo crea si no existe; de forma manual:

```powershell
Copy-Item config/environments.example.json config/environments.json
```

```json title="config/environments.json"
{
  "prod": {
    "url": "https://vcenter-prod.example.local/sdk",
    "credentialTarget": "govc:prod",
    "mode": "confirm",
    "datacenter": "DC-PROD",
    "cluster": "CL-PROD-01",
    "datastore": "DS-PROD-01",
    "network": "PG-Servidores",
    "folder": "/DC-PROD/vm/Servidores",
    "resourcePool": "/DC-PROD/host/CL-PROD-01/Resources",
    "insecure": false,
    "caCerts": "C:/certs/vcenter-ca.pem",
    "persistSession": false
  }
}
```

| Campo | Obligatorio | Descripción |
|---|---|---|
| `url` | Sí | URL del SDK de vCenter, sin usuario ni contraseña |
| `mode` | Sí | `readonly`, `confirm` o `lab` (ver [modos de entorno](/vcenter/seguridad/modelo/#modos-de-entorno)). Si se omite, se aplica `readonly` |
| `credentialTarget` | No | Nombre de la credencial en Credential Manager. Por defecto, `govc:<entorno>` |
| `datacenter`, `datastore`, `network`, `folder`, `resourcePool` | No | Valores por defecto que evitan ambigüedades en las operaciones |
| `cluster` | No | Clúster de referencia para comandos y skills |
| `caCerts` | Recomendado | Certificado de la autoridad interna para validar TLS |
| `insecure` | No | `true` omite la validación TLS. **No utilizar en producción ni en contingencia** |
| `persistSession` | No | `true` conserva la sesión en `~/.govmomi`. Por defecto, `false` |
| `batchTimeoutSec` | No | Tiempo máximo, en segundos, de cada comando en [modo lote](/vcenter/uso/wrapper/#modo-lote-una-sesión-por-corrida). Por defecto, `600` |

**Configuración recomendada:** `dr` en `readonly`, `prod` en `confirm` y `lab` en `lab`.

## Registro de credenciales

<Steps>

1. Abrir una **terminal propia**, fuera de Claude Code, y ejecutar:

   ```powershell
   task credential ENV=prod
   ```

   El usuario puede indicarse de antemano con `ACCOUNT` (opcional): `task credential ENV=prod ACCOUNT=svc-govc-ro@vsphere.local`. La tarea ejecuta `./scripts/Set-GovcCredential.ps1`, que también puede invocarse directamente.

2. Ingresar el usuario (si no se indicó `ACCOUNT`) y, cuando `cmdkey` lo solicite, la contraseña. La contraseña no se muestra, no pasa por argumentos ni queda en el historial.

3. Verificar la conexión:

   ```powershell
   task env ENV=prod
   ```

   Equivale a `./scripts/govc.ps1 -Env prod about`.

</Steps>

<Tabs>
<TabItem label="Rotación">

```powershell
task credential ENV=prod   # reemplaza la credencial existente
```

</TabItem>
<TabItem label="Eliminación">

`task credential` no admite la eliminación; se usa el script directamente:

```powershell
./scripts/Set-GovcCredential.ps1 -Env prod -Remove
```

</TabItem>
<TabItem label="Desde una sesión de Claude">

Si falta la credencial, Claude indica el entorno afectado y solicita que una persona la registre en **su propia terminal**, fuera de Claude Code. Los comandos con el prefijo `!` se ejecutan dentro de la sesión de Claude Code y heredan su entorno, por lo que no sirven para este fin: tanto el script como `task credential` rechazan su ejecución cuando detectan una sesión de Claude Code (variable `CLAUDECODE`).

</TabItem>
</Tabs>

:::caution[Cuentas de servicio]
Se recomienda separar una cuenta de **solo lectura** para reportes y auditorías, y otra con privilegios de **provisión** acotados a carpetas y pools definidos. Para ello, crear dos perfiles (por ejemplo, `prod-ro` en modo `readonly` y `prod-rw` en modo `confirm`) con `credentialTarget` distintos. Los roles deben validarse con el área que administra vCenter.
:::
