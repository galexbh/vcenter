## Perfiles de entorno

Cada entorno se define en `config/environments.json`. Este archivo contiene nombres de servidores internos y **no se versiona**; se parte de la plantilla incluida. `task setup` lo crea si no existe; de forma manual:

```powershell
Copy-Item config/environments.example.json config/environments.json
```

```json title="config/environments.json"
{
  "prod": {
    "url": "https://vcenter-prod.example.local/sdk",
    "credentialTarget": "govc:prod",
    "mode": "confirm",
    "datacenter": "DC-PROD",
    "cluster": "CL-PROD-01",
    "datastore": "DS-PROD-01",
    "network": "PG-Servidores",
    "folder": "/DC-PROD/vm/Servidores",
    "resourcePool": "/DC-PROD/host/CL-PROD-01/Resources",
    "insecure": false,
    "caCerts": "C:/certs/vcenter-ca.pem",
    "persistSession": false,
    "batchParallel": 1
  }
}
```

| Campo | Obligatorio | Descripción |
|---|---|---|
| `url` | Sí | URL del SDK de vCenter, sin usuario ni contraseña |
| `mode` | Sí | `readonly`, `confirm` o `lab` (ver [modos de entorno](/vcenter/seguridad/modelo/#modos-de-entorno)). Si se omite, se aplica `readonly` |
| `credentialTarget` | No | Nombre de la credencial en Credential Manager. Por defecto, `govc:<entorno>` |
| `datacenter`, `datastore`, `network`, `folder`, `resourcePool` | No | Valores por defecto que evitan ambigüedades en las operaciones |
| `cluster` | No | Clúster de referencia para comandos y skills |
| `caCerts` | Recomendado | Archivo PEM con la autoridad certificadora que firmó el certificado TLS de vCenter (ver [certificados de la CA](#certificados-de-la-ca-cacerts)) |
| `insecure` | No | `true` omite la validación TLS. **No utilizar en producción ni en contingencia** |
| `persistSession` | No | `true` conserva la sesión en `~/.govmomi`. Por defecto, `false` |
| `batchTimeoutSec` | No | Tiempo máximo, en segundos, de cada comando en [modo lote](/vcenter/uso/wrapper/#modo-lote-una-sesión-por-corrida). Por defecto, `600` |
| `batchParallel` | No | Número máximo de comandos que el [modo lote](/vcenter/uso/wrapper/#concurrencia-del-lote-batchparallel) ejecuta a la vez con la misma sesión. Por defecto, `1` (en secuencia). Aumenta la carga sobre vCenter: se valida primero en `lab` antes de habilitarlo en `prod` o `dr` |

**Configuración recomendada:** `dr` en `readonly`, `prod` en `confirm` y `lab` en `lab`. La plantilla define `batchParallel` en `4` para `lab` y en `1` para `dr` y `prod`.

## Certificados de la CA (`caCerts`)

`caCerts` no es un certificado que se genere en este proyecto. Es el certificado de la **autoridad certificadora (CA) que firmó el certificado TLS de vCenter**. govc lo utiliza para comprobar que la conexión se establece con el vCenter legítimo y no con un intermediario. Es información pública, no un secreto; el wrapper lo entrega a govc como `GOVC_TLS_CA_CERTS`.

### Origen según el emisor

| Emisor del certificado de vCenter | Quién dispone de la CA | Cómo obtenerla |
|---|---|---|
| **VMCA**, la CA interna de vCenter (configuración por defecto) | El propio vCenter | Descarga desde `https://<vcenter>/certs/download.zip` |
| **CA corporativa** (certificado reemplazado por uno de la PKI de la organización, por ejemplo AD CS) | Equipo de PKI o Seguridad de la Información | Solicitar la raíz y las intermedias en formato PEM |

Para identificar el caso, se abre `https://<vcenter>` en el navegador y se revisa el emisor del certificado (icono del candado). Un emisor del tipo `CA, O=vsphere.local` corresponde a VMCA; el nombre de la CA de la organización corresponde a una CA corporativa.

### Obtención desde VMCA

<Steps>

1. Descargar `https://<vcenter>/certs/download.zip`. El enlace también figura en la página de inicio de vCenter como *Descargar certificados de CA raíz de confianza*.

2. Descomprimir el archivo. La carpeta `certs/win/` contiene los certificados raíz en archivos `.crt`; puede haber más de uno si la VMCA se regeneró.

3. Comprobar el formato. Si el archivo comienza con `-----BEGIN CERTIFICATE-----`, ya está en PEM. Si es binario (DER), convertirlo:

   ```powershell
   certutil -encode .\certs\win\<archivo>.crt C:\certs\vcenter-ca.pem
   ```

   Si hay varios certificados, se concatenan en un único archivo `.pem`.

4. **Validar la huella** del certificado antes de confiar en él (ver la advertencia siguiente):

   ```powershell
   certutil -hashfile C:\certs\vcenter-ca.pem SHA256
   ```

5. Configurar el perfil con `"caCerts": "C:/certs/vcenter-ca.pem"` e `"insecure": false`, y verificar con `task env ENV=<entorno>`.

</Steps>

:::caution[Validación de la huella]
La primera descarga se realiza sin una CA de confianza, por lo que podría ser interceptada. La huella SHA-256 debe compararse con la que proporcione Infraestructura por un canal independiente, en especial para `prod` y `dr`. `certutil -hashfile` calcula la huella del archivo; si se compara con la que muestra el navegador, se calcula sobre el `.crt` original.
:::

### Cuándo no es necesario

Si la raíz de VMCA o de la CA corporativa ya está instalada en el almacén de Windows *Entidades de certificación raíz de confianza* (por ejemplo, distribuida por GPO), govc la toma del sistema. En ese caso `caCerts` puede dejarse vacío.

### Consideraciones

- El archivo se guarda fuera del repositorio (por ejemplo, `C:/certs/`). Si se coloca dentro, no debe versionarse.
- Cuando vCenter renueva o reemplaza su CA, hay que actualizar el archivo; el síntoma es el error `x509: certificate signed by unknown authority` (ver [solución de problemas](/vcenter/referencia/solucion-problemas/)).
- `insecure: true` desactiva precisamente esta verificación: solo es aceptable en `lab` o con el simulador.
- La CA que corresponde a cada entorno y su huella esperada las confirma Infraestructura (equipo dueño de vCenter) junto con Seguridad de la Información.

## Registro de credenciales

<Steps>

1. Abrir una **terminal propia**, fuera de Claude Code, y ejecutar:

   ```powershell
   task credential ENV=prod
   ```

   El usuario puede indicarse de antemano con `ACCOUNT` (opcional): `task credential ENV=prod ACCOUNT=svc-govc-ro@vsphere.local`. La tarea ejecuta `./scripts/Set-GovcCredential.ps1`, que también puede invocarse directamente.

2. Ingresar el usuario (si no se indicó `ACCOUNT`) y, cuando `cmdkey` lo solicite, la contraseña. La contraseña no se muestra, no pasa por argumentos ni queda en el historial.

3. Verificar la conexión:

   ```powershell
   task env ENV=prod
   ```

   Equivale a `./scripts/govc.ps1 -Env prod about`.

</Steps>

<Tabs>
<TabItem label="Rotación">

```powershell
task credential ENV=prod   # reemplaza la credencial existente
```

</TabItem>
<TabItem label="Consulta">

```powershell
task credential:list   # entorno, destino, si está registrada y usuario; nunca la contraseña
```

Equivale a `./scripts/Set-GovcCredential.ps1 -List`. Incluye las entradas `govc:*` que no corresponden a ningún perfil.

</TabItem>
<TabItem label="Eliminación">

```powershell
task credential:remove ENV=prod   # solicita confirmación
```

Equivale a `./scripts/Set-GovcCredential.ps1 -Env prod -Remove`.

</TabItem>
<TabItem label="Desde una sesión de Claude">

Si falta la credencial, Claude indica el entorno afectado y solicita que una persona la registre en **su propia terminal**, fuera de Claude Code. Los comandos con el prefijo `!` se ejecutan dentro de la sesión de Claude Code y heredan su entorno, por lo que no sirven para este fin: tanto el script como `task credential` rechazan su ejecución cuando detectan una sesión de Claude Code (variable `CLAUDECODE`).

</TabItem>
</Tabs>

:::caution[Cuentas de servicio]
Se recomienda separar una cuenta de **solo lectura** para reportes y auditorías, y otra con privilegios de **provisión** acotados a carpetas y pools definidos. Para ello, crear dos perfiles (por ejemplo, `prod-ro` en modo `readonly` y `prod-rw` en modo `confirm`) con `credentialTarget` distintos. Los roles deben validarse con el área que administra vCenter.
:::
